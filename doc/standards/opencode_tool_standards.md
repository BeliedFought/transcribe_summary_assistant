# Стандарт написания кастомных tools для opencode. Версия 4.10.0

Документ описывает правила создания кастомных tools для opencode: расположение и именование, контракт определения `tool()`, схему аргументов, поле `description`, тонкую обертку с внешним скриптом, вывод и ошибки для агента, права и работу с мутациями. Является дополнением к `doc/standards/project_standards.md` и применяется поверх него.

Смежный документ - `doc/standards/skill_anthropic_standards.md` (навыки формата SKILL.md). Выбор между кастомным tool и навыком - раздел 01.02. Все требования основного стандарта остаются в силе, кроме случаев, явно описанных в данном документе.

## 01.01. Назначение и применимость

*Обязательно.*

Кастомный tool - функция, которую модель opencode вызывает в диалоге наравне со встроенными инструментами (`bash`, `read`, `edit`, `grep` и другими). Модель видит три элемента контракта: имя, описание и схему аргументов; реализация ей недоступна. Tool дает доступ к детерминированной операции без загрузки методики и без improvisation через `bash`.

Основной целевой инструмент настоящего стандарта - **opencode**; первоисточник контракта - раздел Custom Tools документации opencode (opencode.ai/docs/custom-tools). Инструменты с иным контрактом (MCP-серверы, плагины) этим документом не регламентируются, связь с ними - разделы 01.02, 01.03.

Настоящий стандарт применять, когда:

- создается кастомный tool в `.opencode/tools/` проекта или `~/.config/opencode/tools/`;
- проектируется обертка над существующим скриптом проекта для вызова агентом;
- ревизируется или дорабатывается существующий кастомный tool.

Стандарт не применяется к: встроенным tools opencode, MCP-серверам (готовая внешняя спецификация; подключение - конфигурация, не разработка), плагинам opencode (за исключением связи через хуки - раздел 01.03).

## 01.02. Выбор между tool и skill

*Обязательно.*

Tool и skill решают разные задачи и не дублируют друг друга:

| Аспект | Кастомный tool | Навык (SKILL.md) |
| ------ | -------------- | ---------------- |
| Суть | Жесткий контракт: имя, схема аргументов, детерминированная реализация | Методика: инструкция, ресурсы, примеры |
| Что видит модель | Имя, `description`, схему аргументов | `name`, `description`, при активации - тело и ресурсы |
| Свобода агента | Только аргументы из схемы | Вся последовательность действий по инструкции |
| Нагрузка на контекст | Описание и схема - постоянно | Метаданные - постоянно, тело - при активации |
| Права | По имени tool в `permission` | По tool `skill` и tool вызова |

Навык с детерминированным скриптом (`skill_anthropic_standards.md`, раздел 03.03) - дефолтный способ упаковки операций проекта: он переносит и контракт, и методику, и примеры. Кастомный tool оправдан, когда:

- операция вызывается часто, и загрузка тела навыка каждый раз избыточна;
- нужна строгая типизация аргументов: ошибка вызова ловится схемой до исполнения;
- нужен адресный permission-gating: `"ask"` / `"deny"` по имени tool;
- операция - часть обвязки репозитория (проверки, сборка, генерация), а не сценарий с методикой.

Признак дублирования: если tool оборачивает скрипт, который уже обернут навыком, и не добавляет ни gating, ни типизацию - tool не нужен. Один сценарий - одна единица: либо навык, либо tool; связка «skill рассказывает когда, tool исполняет как» допустима, если методика реально нужна.

MCP-сервер - выбор, когда функциональность уже есть в готовом сервере или нужна за пределами opencode. Если операция завязана на код и данные проекта, свой tool предпочтительнее: меньше внешних зависимостей, контрактом управляет репозиторий.

## 01.03. Расположение

*Обязательно.*

opencode обнаруживает кастомные tools в двух каталогах:

| Область | Каталог | Хранение |
| ------- | ------- | -------- |
| Проектные tools | `<repo>/.opencode/tools/` | В репозитории, коммитятся вместе с проектом |
| Личные tools | `~/.config/opencode/tools/` | Вне репозиториев, на машине |

Правила:

- Проектный tool (завязан на код, скрипты и данные репозитория) - только в `.opencode/tools/` этого репозитория. Личный tool (не зависит от репозитория) - в `~/.config/opencode/tools/`.
- Исходники внешних скриптов, вызываемых tool, хранятся в структуре проекта (`run/`, `scripts/` - по основному стандарту), а не внутри `.opencode/tools/`; в каталоге tools - только определения контрактов.
- Имя файла = имя tool (раздел 02.01). Кастомный tool с именем встроенного переопределяет его - **запрещено** без явного запроса пользователя; для отключения встроенного tool используется `permission`, а не переопределение.
- Кросс-инструментная логика (валидация аргументов, защита путей, подстановка env, модификация вызовов всех tools) - в плагинах opencode через хуки `tool.execute.before` / `tool.execute.after`, а не в каждом tool. Признак выноса: правило нужно всем tools сразу.
- Логирование из оберток - структурированное, без засорения результата tool; `console.log` обертки в результат вызова не попадает.

## 01.04. Именование

*Обязательно.*

| Объект | Правило | Пример |
| ------ | ------- | ------ |
| Файл и tool | Латиница, `snake_case`, глагол + объект от общего к частному | `run_report.ts`, `db_check_connection.ts` |
| Неймспейс | Префикс домена для группы однородных tools | `db_*`, `report_*`, `etl_*` |
| Аргументы | `snake_case`, однозначные, с уточнителем вместо голого существительного | `report_name`, `source_db`, не `name`, не `db` |
| Экспорты (несколько tools в файле) | Имя генерируется как `<файл>_<экспорт>`; считать это запасным вариантом, дефолт - один tool на файл | `checks_schema`, `checks_data` |

Имя должно различать tool среди соседних: пересекающиеся имена и назначения путают модель при выборе. Имя отражает операцию, а не реализацию: `search_logs`, а не `grep_wrapper`.

## 02.01. Определение tool()

*Обязательно.*

Единственный канонический вид - хелпер `tool()` из `@opencode-ai/plugin`:

```typescript
import { tool } from "@opencode-ai/plugin"

export default tool({
  description: "Краткое описание назначения и применимости (раздел 02.03)",
  args: {
    report_name: tool.schema.string().describe("Имя отчета из каталога отчетов проекта")
  },
  async execute(args, context) {
    // только запуск внешнего скрипта и формирование ответа
  }
})
```

Правила:

- Файл экспортирует ровно один `default` tool; несколько именованных экспортов дают имена `<файл>_<экспорт>` - использовать только при тесно связанной группе.
- Реализация получает `args` (проверены схемой) и `context`: `agent`, `sessionID`, `messageID`, `directory`, `worktree`. Рабочие пути брать из `context.worktree` / `context.directory`; **требовать от модели путь к проекту параметром запрещено**.
- Альтернатива - plain-объект со схемой Zod; допустима, но хелпер `tool()` предпочтителен (типизация и валидация).
- Обертка не содержит бизнес-логики (раздел 03.01) и не создает побочных эффектов сверх вызова скрипта.

## 02.02. Аргументы и схема

*Обязательно.*

- Каждый аргумент - через `tool.schema` (Zod) с собственным `.describe()`; описание аргумента читает модель - формат, единицы, допустимые значения.
- Минимум аргументов: обязательное - только то, чего модель не может знать сама (имя отчета, идентификатор сущности). Все остальное - дефолты внутри реализации.
- Составные схемы (enum, объединения) описывать в `.describe()` перечислением допустимых значений.
- Пример корректного вызова - в `.describe()` или `description`, если формат входа неочевиден.
- Запрещено: параметры-флаги, дублирующие permission (секреты, подтверждение деструктивности - не аргументы, а права, раздел 04); параметры контекста сессии (раздел 02.01).

## 02.03. Поле description

*Обязательно.*

`description` - главный фактор выбора tool моделью; писать для модели, не для человека. Канон:

- что делает tool, затем когда применять и когда не применять;
- что возвращает и в каком объеме;
- ограничения: read-only или мутация, требования к окружению, стоимость вызова;
- конкретные формулировки из реальных запросов пользователя;
- без маркетинга («powerful», «easy to use») и без пересказа реализации.

| Плохо | Хорошо |
| ----- | ------ |
| `Runs a report` | `Генерирует отчет по имени из каталога отчетов проекта: HTML, Excel и JSON в output/. Use when the user asks for готовый отчет по имени. Не выполняет ad-hoc SQL - для этого execute_mssql` |
| `Database tool` | `Проверяет соединения со всеми БД из секций db_* конфига и выводит статус каждой. Read-only. Use when diagnosing connectivity before queries` |

Формулировка - часть контракта: при повторяющихся ошибочных вызовах модели править `description` и `.describe()` аргументов, а не усложнять реализацию (см. чеклист, раздел 05.03).

## 03.01. Тонкая обертка и внешний скрипт

*Обязательно.*

Определение tool - TypeScript, логика - язык проекта. Обертка делает ровно три вещи: описывает контракт, запускает внешний скрипт, формирует ответ.

```typescript
import { tool } from "@opencode-ai/plugin"
import path from "path"

export default tool({
  description: "См. раздел 02.03",
  args: {
    report_name: tool.schema.string().describe("Имя отчета из каталога отчетов")
  },
  async execute(args, context) {
    const script = path.join(context.worktree, "run", "reports", "build_report.py")
    const result = await Bun.$`python3 ${script} --name ${args.report_name}`
    return result.text().trim()
  }
})
```

Правила:

- Вся логика - во внешнем скрипте проекта (`run/`, `scripts/`); обертка без `if` бизнес-логики. Скрипт тестируем и переиспользуем независимо от opencode.
- Скрипт не зависит от текущего рабочего каталога - только на переданные аргументы и пути от `context.worktree`.
- Вывод и текст скриптов - по основному стандарту: строки `YYYY-MM-DD HH:MM:SS [маркер] сообщение`, монохромный stdout без ANSI-цветов и рамок, маркеры `[!]` / `[i]` / `[*]`, текст по разделу 04.03 (русский, без точки в конце сообщений, без `ё`/`Ё`, тире - только дефис-минус), коды завершения 0 / 1 / 2 (`project_standards.md`, разделы 04.02 - 04.04, 05.03).
- Зависимости скрипта - в зависимостях проекта (`requirements.txt`); обертка зависимости не добавляет.
- Шум скрипта (стектрейсы, прогресс, тайминги) фильтрует обертка: успех - краткая отметка, полный вывод - только при ненулевом коде завершения.

## 03.02. Вывод для агента

*Обязательно.*

Возврат tool читает модель для выбора следующего шага; проектировать ответ под нее, а не под человека:

- только высокосигнальные данные; без технических идентификаторов (uuid, mime-типы), если они не нужны в цепочке вызовов; человекочитаемые имена вместо суррогатных ключей, когда выбор объекта идет по смыслу;
- усечение - обязанность обертки, не модели: разумные дефолты объема, ориентир - до 25 тыс. токенов на ответ; полный объем - в файл-артефакт с путем в ответе;
- параметр `response_format` (`concise` / `detailed`) - если одному tool нужны оба режима; идентификаторы для последующих вызовов - только в `detailed`;
- структура ответа стабильна между вызовами: одинаковые поля в одинаковом порядке - модель опирается на формат;
- пагинация или фильтр аргументами - для потенциально больших выборок, до запроса, а не после.

## 03.03. Ошибки

*Обязательно.*

- Сообщение об ошибке - конкретное исправимое действие с примером корректного ввода; без сырых кодов и трейсбеков в ответе tool.
- Ошибку исполнения возвращать в результате (строкой, с маркером `[!]` скрипта), а не пробрасывать необработанное исключение: модель должна увидеть сбой и скорректировать вызов.
- Классы ошибок разделять явно: ошибка использования (невалидные аргументы - код 2) и ошибка исполнения (окружение, данные - код 1) - `project_standards.md`, раздел 05.03.
- Повторно воспроизводимую диагностику - отдельным read-only tool (`*_check`), а не текстом внутри другого tool.

## 04.01. Права (permissions)

*Обязательно.*

- Read-only tool - дефолт. Мутирующий tool обязательно получают запись в `opencode.json`:

```json
{
  "permission": {
    "report_run": "allow",
    "db_execute": "ask",
    "deploy_*": "ask"
  }
}
```

- Имя tool в `permission` - полноценный ключ наравне со встроенными; поддерживаются wildcard-маски.
- Деструктивные и необратимые операции - `"ask"` минимум; автоматический запуск (`"allow"`) - только для идемпотентных read-only операций.
- Секреты - через переменные окружения и подстановки конфига; в `description`, схеме и коде обертки секретов нет (`project_standards.md`, раздел 05).
- Минимальный набор tools в контексте: неиспользуемые tool удалять, а не отключать - каждое описание расходует контекст на каждом шаге.

## 04.02. Мутации и детерминизм

*Обязательно.*

- Детерминированное предпочтительнее выбора моделью: если известно, что именно нужно, решение фиксируется в реализации, а не отдается аргументом на усмотрение модели.
- Идемпотентность: повторный вызов с теми же аргументами не меняет результат среды повторно; неидемпотентные операции - только через `"ask"`.
- Мутирующие операции - с поддержкой `--dry-run` по основному стандарту (`project_standards.md`, раздел 03.04); dry-run-режим exposed аргументом, помеченным в `.describe()`.
- Состояние между вызовами tool не хранить: каждый вызов самодостаточен, промежуточные данные - файлы проекта или хранилище проекта.

## 05.01. Антипаттерны

*Обязательно.*

| Антипаттерн | Правильно |
| ----------- | --------- |
| Обертка REST API один к одному (по методу на tool) | Tools под рабочие сценарии агента; меньше и емче |
| `list_*` там, где нужен поиск | `search_*` с фильтром и релевантными строками |
| Описание-заглушка из одной фразы | WHAT + WHEN + ограничения (раздел 02.03) |
| Сырой трейсбек в ответе | Исправимое действие и пример корректного ввода (раздел 03.03) |
| Полный дамп логов и вывода тестов | Краткая отметка, артефакт с путем, полный вывод только при ошибке (раздел 03.02) |
| Модель truncирует вывод сама (`head`, лимиты наугад) | Дефолты усечения в обертке |
| Перекрывающиеся tools с размытыми назначениями | Разные четкие назначения; пересечение - объединить |
| Переопределение встроенного tool | Запрещено без явного запроса; отключение - через `permission` (раздел 01.03) |
| Бизнес-логика в TypeScript-обертке | Логика во внешнем скрипте проекта (раздел 03.01) |
| Зависимость скрипта от cwd и абсолютных путей машины | Аргументы и `context.worktree` (раздел 03.01) |
| Секреты в схеме, коде или `description` | Переменные окружения и конфиг проекта (раздел 04.01) |
| Дублирование skill'а tool'ом без новых свойств | Одна единица на сценарий; связка - только при реальной пользе (раздел 01.02) |
| Параметры контекста сессии у модели | `context.worktree` / `context.directory` (раздел 02.01) |
| Tool «на всякий случай» без реальных вызовов | Удалить; контекст агента - ограниченный ресурс (раздел 04.01) |

## 05.02. Пример

Проектный tool-диспетчер отчетов: тонкая обертка над существующим скриптом проекта, один tool на группу операций.

```text
<repo>/
├── .opencode/
│   └── tools/
│       └── run_report.ts        # контракт tool
├── run/
│   └── reports/
│       └── build_report.py      # реализация: SQL, HTML, Excel, JSON
└── opencode.json                # permissions проекта
```

`run_report.ts`:

```typescript
import { tool } from "@opencode-ai/plugin"
import path from "path"

export default tool({
  description:
    "Генерирует готовый отчет проекта по имени: пишет HTML, Excel и JSON в output/ и возвращает пути и KPI. " +
    "Use when the user asks for готовый отчет по имени из каталога отчетов. " +
    "Не выполняет произвольный SQL - для разведки данных использовать прямой SQL через БД-инструменты",
  args: {
    report_name: tool.schema
      .string()
      .describe("Имя отчета из каталога отчетов проекта, например items_units_diff"),
    dry_run: tool.schema
      .boolean()
      .optional()
      .describe("true - показать план без записи файлов; дефолт false")
  },
  async execute(args, context) {
    const script = path.join(context.worktree, "run", "reports", "build_report.py")
    const dry = args.dry_run ? " --dry-run" : ""
    const result = await Bun.$`python3 ${script} --name ${args.report_name}${dry}`
    return result.text().trim()
  }
})
```

`opencode.json`:

```json
{
  "permission": {
    "run_report": "allow"
  }
}
```

## 05.03. Чеклист автора

Перед публикацией tool проверить:

- [ ] Контракт нужен: не дублирует навык и не оборачивает API один к одному (раздел 01.02)
- [ ] Файл в правильном каталоге: проектный - `.opencode/tools/` репозитория, личный - `~/.config/opencode/tools/` (раздел 01.03)
- [ ] Имя файла = имя tool, `snake_case`, глагол + объект, не конфликтует со встроенными (разделы 01.04, 02.01)
- [ ] Определение через `tool()`; рабочие пути из `context`, не параметрами (раздел 02.01)
- [ ] Каждый аргумент со своим `.describe()`; обязательных аргументов минимум (раздел 02.02)
- [ ] `description`: WHAT + WHEN + ограничения + состав ответа (раздел 02.03)
- [ ] Логика - во внешнем скрипте; обертка только запускает и формирует ответ (раздел 03.01)
- [ ] Скрипт не зависит от cwd; вывод - по формату маркеров основного стандарта; коды завершения 0 / 1 / 2 (раздел 03.01)
- [ ] Ответ - высокосигнальный, усеченный оберткой, с артефактом для полного объема (раздел 03.02)
- [ ] Ошибки - исправимыми сообщениями с примером ввода, без трейсбеков (раздел 03.03)
- [ ] Мутирующий tool - в `permission` с `"ask"` минимум; read-only можно `"allow"` (раздел 04.01)
- [ ] Мутации идемпотентны или защищены; есть `--dry-run` (раздел 04.02)
- [ ] Секретов в файле нет (раздел 04.01)
- [ ] Tool проверен на реальных запросах: выбирается моделью по `description`, ошибки вызова отсутствуют; при ошибках выбора правились описания, не реализация
